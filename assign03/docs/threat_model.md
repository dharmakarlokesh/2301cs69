# Threat model — educational wallet (`toywallet`)

**Assets:** the private key, which authorises spending; the integrity of what the user believes they
are signing (recipient, amount, network); and the uniqueness of each authorised payment.
**Trust boundary:** the user's machine and this CLI. The network, clipboard, websites, and any
other process on the machine are untrusted.

| # | Threat | Attack | Mitigation in this wallet | Residual risk / what a real wallet adds |
|---|---|---|---|---|
| 1 | **Key theft** | Malware or another user reads the key file; the key leaks via git, backups, logs, or a screen share | Key file created with `O_EXCL` and mode **0600**; the wallet **refuses to load** a key file readable by group or others; the private key is **never printed** (`keygen` exports only public data); `*.dev-key.json` is in `.gitignore`; the file carries a conspicuous **TEST-ONLY** warning that is echoed on every load | Stored **unencrypted**, so anything running as the user can read it. Real wallets encrypt with a passphrase (scrypt or Argon2 plus AEAD), use OS keychains or hardware wallets and secure elements, and keep the key off the online machine |
| 2 | **Weak randomness** | A predictable RNG (seeded with time, `random` module, VM snapshot clone) lets an attacker recompute the key; ECDSA **nonce `k` reuse** leaks the key from two signatures | The private scalar comes from the **OS CSPRNG** (`secrets.token_bytes` → `getrandom`) with rejection sampling for `1 ≤ k < n`; ECDSA signing and its per-signature nonce are done by OpenSSL via `cryptography`; **no home-made EC math or RNG** | A compromised OS RNG or a cloned VM state is out of scope. Production signers use deterministic RFC 6979 nonces (optionally hedged with extra randomness) |
| 3 | **Replay** | An attacker re-broadcasts a valid signed transaction to pay Bob twice, or replays it on another network | Every transaction has a **nonce**; the verifier keeps a persisted per-sender high-water mark (`--nonce-db`) and rejects `nonce ≤ last`. **`network_id` is inside the signed bytes**, plus a fixed **domain tag**, so a signature is valid for one network and one protocol only | Nonce state must be kept consistently by every validator (in a real chain this is consensus state). Gaps are allowed, so a held-back transaction with a higher nonce can still be submitted later; expiry fields would address this |
| 4 | **Clipboard replacement** | Clipper malware swaps a copied address for the attacker's look-alike | **Base58Check checksum** catches typos and corruption (a random error is undetected with probability 2⁻³²); the CLI prints sender → recipient and the amount on verify | A checksum **cannot** catch a *valid* attacker address. Users must compare the **whole** address on a trusted display (hardware wallet screen); real wallets use address books and allowlists, and warn when a pasted address differs from the copied one |
| 5 | **Phishing / blind signing** | A malicious site or tool hands the user a transaction to "just sign" with a different recipient or amount, or tricks them into revealing the key file | The wallet signs only the **fixed canonical layout**. It re-parses the JSON strictly (exact keys, no floats, no duplicate keys, integer units), so hidden fields or ambiguous values cannot slip in. It **refuses to sign** if the key doesn't own `sender` | The user must still read what they sign. Real wallets show a human-readable summary on a trusted screen, use EIP-712-style typed data, and never ask for a seed or key file over the web |
| 6 | **Accidental mainnet use** | A test key, script, or address is used against a real network and real funds | **Separate address version bytes** (`0x6F` testnet vs `0x00` mainnet), so a testnet address is rejected on mainnet and vice versa. `network_id` is signed, and the verifier rejects any `network_id` other than its own. Key files are labelled TEST-ONLY. The default network is `course-testnet` | Nothing stops a user from deliberately generating a `course-mainnet` key; a real wallet would keep the profiles separate and add a confirmation step |
| 7 | Signature malleability | A third party flips `s → n − s` or re-encodes the DER to change the txid without the key | **Strict DER** plus **low-S** are enforced on verify; the signer always normalises to low-S; `txid` hashes the signing bytes, not the signature | — |
| 8 | Ambiguous serialization | Two JSON spellings of the same transaction hash differently, or one spelling means two things | Fixed binary layout, integers only, exact field set, so whitespace and key order are irrelevant (tested) | — |

## Out of scope

Side channels against OpenSSL, physical attacks, consensus or double-spend at the ledger level
(Assignment 4), and network-level privacy.
